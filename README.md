# IoT / SCADA Telemetry Anomaly Detection

Detecting abnormal sensor behaviour in industrial telemetry with machine
learning — an extension of my ENSAM SCADA supervision work (Node-RED, MQTT,
ESP32) into data science: the same kind of temperature / humidity / vibration
streams, now analysed instead of only displayed.

## Why labeled synthetic data?

You cannot measure an anomaly detector without ground truth. Real factory
telemetry rarely comes labeled, so this project generates realistic sensor
series (daily cycles, measurement noise, slow drift) and **injects known
anomalies with labels**. Every metric reported here is therefore measured
against known answers — precision and recall mean something.

## Dataset (generated, committed)

`data/telemetry.csv` — 7 days of minute-level telemetry, generated by
`src/telemetry_generator.py` with seed 42 (fully reproducible):

| | |
|---|---|
| Rows | 10,080 |
| Sensors | temperature (°C), humidity (%), vibration (mm/s) |
| Labeled anomalies | 404 (4.01%) |
| — drift (temperature, ~2 h ramps) | 240 |
| — stuck (vibration frozen 30–60 min) | 120 |
| — drop (humidity, 5–15 min) | 29 |
| — spike (temperature, 1–3 min) | 15 |

## API

```bash
uvicorn src.api:app --port 8000
```

- `GET /health` — service and model status.
- `GET /model-info` — the measured metrics below, served from `results/metrics.json`.
- `POST /detect` — body: `{"records": [{"timestamp": ..., "temperature": ..., "humidity": ..., "vibration": ...}, ...]}`
  with at least 31 consecutive minute records (the first 29 are feature
  context; predictions start at index 29). Returns per-point flags and the
  anomaly count. The model is loaded from `models/isolation_forest.joblib`
  when present, otherwise trained on the spot from the committed dataset
  with the same protocol as the evaluation.

## Dashboard

```bash
streamlit run src/dashboard.py
```

Pick a day and the sensors to display: the series are plotted with the
model's predicted anomalies as red dots and (optionally) the ground-truth
labels as green circles, plus the day's counts and the measured test-period
metrics. Verified on day 1 of the dataset: 1,411 points scored, 79 predicted
anomalies against 120 labeled ones.

## Live MQTT mode

The same publish/subscribe pattern as the SCADA coursework: JSON records on
the topic `factory/telemetry`, scored as they arrive.

```bash
python -m src.mqtt_live --broker localhost        # subscriber (the detector)
python -m src.mqtt_simulator --broker localhost   # replays the dataset as a feeder
```

Verified end to end against a local broker: 120 replayed records produced
91 scored points (scoring starts once 31 records give the features context),
and a manually published 45 °C reading was flagged as an anomaly.

## Measured results

Chronological split: the model is fitted on the first 3 days only and both
detectors are scored on the remaining 4 days (5,760 points, 274 labeled
anomalies). Reproduce with `python -m src.evaluate_detectors`; the full
output is in `results/metrics.json`.

| Detector | Precision | Recall | F1 |
|---|---|---|---|
| Baseline (rolling z-score, window 60 min, threshold 3.5) | 0.490 | 0.091 | 0.154 |
| Isolation Forest (12 features, contamination 0.04) | 0.234 | 0.339 | 0.277 |

Recall per anomaly type — where each detector is blind:

| Type | Baseline | Isolation Forest |
|---|---|---|
| spike | 1.000 | 1.000 |
| drop | 0.381 | 0.905 |
| drift | 0.000 | 0.308 |
| stuck | 0.033 | 0.200 |

Reading: a threshold catches sudden spikes perfectly but is blind to slow
drift (its rolling mean adapts to the drift) and to stuck sensors (a frozen
value is never "far" from its mean). The Isolation Forest catches most drops
and part of the drifts, at the price of many false alarms (precision 0.234).
Neither is good enough alone on stuck sensors — that is stated openly here
because it is what the measurements say, and it motivates the feature and
tuning work in the next modules.

## Honest limits

Synthetic telemetry is cleaner than real factory data: no missing packets, no
sensor miscalibration beyond what is simulated. The natural next steps are a
public benchmark (e.g. SWaT) or captures from a real ESP32 feed. Metrics in
this README are always produced by running the code in this repo — never
estimated.
